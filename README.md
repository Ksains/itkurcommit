# Сайт IT-раздела

Участники через Git добавляют карточки о себе. При желании они также описывают идею проекта. Все принятые карточки отображаются на общем сайте.

## Как это работает

1. Участник делает Fork общего репозитория и создаёт рабочую ветку.
2. Заполняет форму на сайте и скачивает файл `логин.json`.
3. Добавляет файл в `participants/`, делает коммит, push и открывает Pull Request.
4. GitHub Actions проверяет карточки, тесты и сборку.
5. Руководитель проверяет содержание и принимает PR.
6. Сервер проверяет основную ветку и автоматически обновляет контейнер. После обновления карточка появляется на сайте.

Один GitHub-логин соответствует одному файлу. Изменение этого файла обновляет карточку. Проверка принадлежности логина автору PR остаётся за руководителем. Данные хранятся в Git, база данных не нужна. Черновик формы сохраняется только в браузере и не публикуется при скачивании.

В форме обязательны имя, GitHub-логин, направление, навыки и информация о себе. Название и описание проекта можно не заполнять. Если идея указана, она появляется в карточке; пустой раздел проекта на сайте не показывается.

## Запуск через Docker Compose

Нужны Docker Engine с Compose v2 (на Windows подойдёт Docker Desktop в режиме Linux containers) и копия репозитория. Node.js на хосте устанавливать не нужно.

Из корня проекта:

```bash
docker compose up -d --build --wait
```

Откройте http://127.0.0.1:8080. Сайт работает по HTTP. Локальный сервер разработки на порту 8000 не мешает контейнеру.

```bash
docker compose ps
docker compose logs --tail=100 web
docker compose down
```

Команды показывают состояние, журнал и останавливают проект соответственно. Карточки останутся в репозитории.

## Развёртывание на сервере

Склонируйте общий репозиторий на сервер и перейдите в его папку. В существующей конфигурации сервера порты 80/443 уже заняты общим прокси. Оставьте адрес привязки `127.0.0.1` и порт `8080` из Compose, если они свободны. Не открывайте порт контейнера наружу без HTTPS. Затем выполните:

```bash
docker compose up -d --build --wait
```

Проверка на самом сервере: `curl -f http://127.0.0.1:8080/data/participants.json`. Для публичного доступа существующий прокси должен обслуживать выбранный домен по HTTPS и передавать запросы этому контейнеру. Если прокси тоже работает в Docker, адрес `127.0.0.1` внутри него указывает на сам прокси. Новый NGINX в этот проект не добавлен.

### Подключение к существующему NGINX

На сервере уже есть NGINX, принимающий 80/443, и путь `/var/www/certbot` для проверки домена. Конфигурацию нового домена создайте на сервере рядом с конфигурациями остальных доменов. Сначала настройте проверку домена по HTTP и получите сертификат; HTTPS-блок с путями к сертификату добавьте после его выдачи.

Для маршрута `proxy_pass http://onboarding-web:8000` NGINX и сайт должны находиться в общей Docker-сети. Узнайте сеть прокси и доступна ли она обычным контейнерам:

```bash
docker inspect ИМЯ_КОНТЕЙНЕРА_NGINX --format '{{json .NetworkSettings.Networks}}'
docker network inspect ИМЯ_СЕТИ --format 'driver={{.Driver}} attachable={{.Attachable}}'
```

Если сеть доступна для подключения, укажите её имя в `.env` как `PROXY_NETWORK=ИМЯ_СЕТИ` и запустите проект с сетевым дополнением:

```bash
docker compose -f compose.yaml -f compose.proxy.yaml up -d --build --wait
```

Это добавит сайту имя `onboarding-web` в общей сети. Проверьте доступность **из контейнера NGINX**: `docker exec ИМЯ_КОНТЕЙНЕРА_NGINX wget -qO- http://onboarding-web:8000/data/participants.json`. Если в образе NGINX нет `wget`, используйте другой HTTP-клиент внутри этой сети. Если сеть Swarm не attachable, не меняйте её вслепую: сначала выберите с администратором сервера способ подключения.

Сначала настройте HTTP-блок в существующем NGINX, проверьте его через `nginx -t` внутри контейнера и перечитайте конфигурацию через `nginx -s reload`. Убедитесь, что DNS домена ведёт на сервер. Затем получите сертификат через уже используемый на сервере Certbot с методом webroot и каталогом `/var/www/certbot`. После появления сертификата добавьте HTTPS-блок и снова выполните проверку и перезагрузку NGINX. Конкретные пути к файлам конфигурации и команда Certbot зависят от текущего развёртывания NGINX; они не входят в этот репозиторий.

После публикации проверьте `https://ВАШ_ДОМЕН/` и `https://ВАШ_ДОМЕН/data/participants.json`. До настройки HTTPS не отправляйте публичную ссылку участникам: по HTTP можно подменить содержимое гайда.

## Обновление после принятия PR

На сервере `/home/egor/itkurcommit` развёрнут из `main`. Один раз после получения обновлённого репозитория установите таймер:

```bash
cd /home/egor/itkurcommit
git pull --ff-only
sudo sh scripts/install-server-auto-update.sh
```

Таймер проверяет `main` каждые две минуты. Если появился новый коммит, скрипт обновляет локальный репозиторий и пересобирает сайт через Compose. Если сборка не удалась, успешная версия не отмечается и следующая проверка повторяет попытку. Логи: `sudo journalctl -u itkurcommit-update.service -n 50 --no-pager`. Проверка таймера: `systemctl list-timers itkurcommit-update.timer`. Для немедленного обновления: `sudo systemctl start itkurcommit-update.service`. После успешного обновления участник обновляет страницу и видит карточку. Замена единственного контейнера может вызвать короткий перерыв в доступности.

Скрипт установки рассчитан на пользователя `egor`, каталог `/home/egor/itkurcommit` и Docker-сеть `verification_default`. Он устанавливает копию скрипта вне репозитория, чтобы изменение файла в PR не меняло выполняемую сервером команду. GitHub-секреты и Deploy Key для публичного репозитория не нужны. Проверка PR описана в `.github/workflows/check.yml`; workflow GitHub Pages остаётся ручным и не обновляет Docker-сайт.

## Что внутри образа

Dockerfile использует две стадии на `node:22-alpine`. Первая запускает тесты, проверяет карточки и собирает `dist/`. Во вторую попадают только готовый сайт и `serve.cjs`, который раздаёт статические файлы. Установка npm-пакетов не требуется. Исходные карточки, тесты и инструменты сборки в рабочий образ не копируются.

Compose запускает процесс без root, с файловой системой только для чтения, проверкой работоспособности, перезапуском и ограничением журналов. Лимит памяти контейнера 128 МБ; это ограничение, а не замер потребления. Постоянные тома не нужны, источник данных — Git. `.dockerignore` исключает из контекста сборки Git, локальные настройки и посторонние файлы.

## Локальная разработка без Docker

Нужен Node.js 22 или новее. Участникам он не требуется.

```bash
node server.cjs
```

Откройте http://127.0.0.1:8000. Для остановки нажмите Ctrl+C.

```bash
node scripts/participants.cjs
node --test tests/test_profiles.cjs tests/test_ui.cjs tests/test_static.cjs
node scripts/build.cjs
```

Сборка создаёт статический сайт в `dist/`, включая `data/participants.json`. Для проверки сервера контейнера без Docker после сборки выполните `node scripts/serve.cjs` из корня проекта (предварительно освободите порт 8000). Этот сервер слушает все сетевые интерфейсы.
